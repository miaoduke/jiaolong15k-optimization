## Q3 电量阈值 Windows 实现研究（核心突破进行中）

### 现状
- Linux：`charge_limit.sh` 直写 EC 0x7B9（uniwill驱动路径）——Windows 无此驱动
- 官方控制台：阈值滑条**不生效**（UI存在但服务未实现写入，与你的观察一致）
- 官方MQTT：`BATTERY_CHARGINGLIMIT_SETTING` 指令存在但**未验证**

### Windows 侧突破口（本轮发现）
**`root\wmi\AcpiTest_MULong`** 类：
```
GetSetULong(UInt64 Data) → UInt32   ← EC RAM 读写口
SetULong(UInt32 Data)               ← 写
GetULong(UInt32 Data) → UInt32      ← 读
```
这正是 Linux 侧报告提到的 "GetSetULong(EC RAM)" WMI 口在 Windows 的暴露形式。

### 待验证（需管理员一次）
桌面已建 **`EC探测(管理员).lnk`** — 双击→UAC点是→结果自动存：
`自制控制台\wmi_probe_result.log`

探测内容：
1. 实例枚举（InstanceName）
2. 读 ProjectID@0x740（应=16，验证编码规则）
3. 读 充电上限@0x7B9（应=0xD0=80%+标志位）
4. 确认编码后 → 自制台电池页增加**真实阈值滑条**（WMI直写EC）

### 如果 WMI 口验证通过，还能解锁
- 风扇曲线直写（0xF00-0xF5F）
- RGB 全协议直控（0x769-76B）
- 所有 EC 寄存器（147个地址）的 Windows 原生读写
