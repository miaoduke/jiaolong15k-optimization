## 二、五项判决性结论

### 1. E1 GPU功耗墙 —— 定案：本机不可为 ⛔
`nvidia-smi -pl 140` 在**管理员权限下同样被驱动拒绝**（current 恒回 115，max=140 仅为报表值）。

GUI 已将按钮标注为「TGP 140W(已仲裁✗)」保留验证入口。

### 2. EC 的 WMI 通路当前失效 —— 最高优先级待查 🔴
`AcpiTest_MULong` 类存在但**实例数为 0**（Get-WmiObject 与 Get-CimInstance 双通道确认），
历史基线'ACPI\PNP0C14\1_0'不再发布。后果链：
- 充电阈值 EC 直写（超越官方的招牌功能）**暂时不可用**
- EC 实时温度/风扇卡无数据源
- E2 实验(0x7C1/0x7C2)无法读基线
方向猜测: ACPI WMI 缓冲区设备需重新枚举（**建议重启后第一时间复测**）/官方5.56安装动了驱动绑定。
注: 两次追加 UAC 被取消，提权侧复测留待下次授权窗口。

### 3. CloseTimer 无回读通路
SET_DETAIL 写入后 GETSTATUS 回包不含该字段，写入是否生效只能靠行为观察。
与键盘亮度同属"盲写类"，GUI 的异步验证会如实显示「⚠️未回读确认」。

### 4. HEALTHYMODE 无参调用不翻档
连发两次档位恒为 2——语义疑似"设为健康档2"而非循环切换。**官方 UI 三档切换的真实载荷
仍是空白**，是替代官方路上最后一个已知协议盲点 → 需用协议学习器抓一次官方电池页操作。

### 5. GETSUPPORT 回包未被路由
发布成功但 Customize/Support 收不到数据——MrConsole 订阅表缺对应回包主题。
影响小（支持位已有手工调研结论），补齐属锦上添花。

# 附录D：WriteEC 定案与充电阈值功能回归（20260825）

## 签名逆向三重证据
1. **字节级对比**(capstone 反汇编 ACPIDriverDll.dll):
   ReadEC 仅保存 ecx→缓冲G[0]; WriteEC 保存 ecx→G[0] **和** edx→G[4](相邻dword), 无指针解引用;
   IOCTL 读=0x9C40A488 / 写=0x9C40A48C; 缓冲经 ACPI 请求包(魔术字 ECRW/AeiC, 操作码 1读/2写)
2. **零破坏 NO-OP 实验**: mem[0x7A9]=100 时调 WriteEC(0x7A9,100),
   监控误写目标 0x64(基线0)全程未变, 0x7A8/0x7A9 纹丝不动 → **WriteEC(addr, value)** 定案
3. **事故复盘**: 前日崩溃源于两参指针签名猜测(整数当指针传入驱动→内核野指针);
   本轮先证"双整型无解引用"再做实验, 方法论闭环

## 充电阈值功能回归(通电实测)
- 新地址对: **0x7A8=起始% / 0x7A9=停止%**(全域扫描发现, 默认 80/100)
- 科学环: 读 80/100 → set 90 → 回读 {80,90} ✅ → 恢复 100 → 回读 {80,100} ✅
- 物理观察: 电量10% < 阈值持续充电(BatteryStatus=2), 符合预期;
  满充截止效果(充至阈值即停)留待日常插电使用验证
- 产品化: `set_charge_limit(percent)`(语义=停止阈值,起始保持) + 回读失败自动恢复原值
