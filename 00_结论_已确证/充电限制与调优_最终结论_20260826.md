## 一、电池充电限制 — 最终结论：本机 EC 固件不支持软件限充

### 结论
GM5BG0E (蛟龙15K/7435H) 主板 EC 固件**没有实现软件充电限制功能**。
无论软件层如何写入，电池都会充电到 100%。官方控制台的三个电池模式（长效/平衡/工作站）
只切换性能策略，不控制充电。

### 压箱证据（本地实测 + 内核文档交叉验证）

1. **阈值寄存器写入无效**：EC 0x7B9(UP)/0x7D0(DOWN) 是官方阈值对，
   裸 IO(ACPIDriverDll) / ACPI层(UWACPIDriver IOCTL) / 官方GCUService 三种通道写入后，
   读回一致但电量仍 76%→100% 上涨，全程充电电流 9-11W。
2. **三档 profile 同样无效**：官方 UI 三档报文为 `{"Action":"HEALTHYMODE/BALANCEDMODE/PERFORMANCEDMODE"}`
   发往 `BatteryProtection/Control`，切换后 EC 充电寄存器纹丝不动，电流仍 10W 持续充电。
3. **真实电流判据**：`root\wmi BatteryStatus` 的 ChargeRate 全程 9-11W、Charging=True、
   RemainingCapacity 真实上涨(59204→59827 mWh)，证明 EC 没有隐藏充电状态，是真在充电到 100%。
4. **内核文档印证**：Linux `drivers/platform/x86/uniwill-laptop` 官方文档明确 —
   *「Some devices do not properly implement the charging threshold interface… The charging profile
   interface will be available instead」*，本机属于两类接口都未生效的机型。

### 被彻底证伪的假设（勿再尝试）
| 假设 | 证伪证据 |
|------|---------|
| 0x7A8/0x7A9 是充电阈值(旧地址) | 正确地址是 0x7B9/0x7D0；旧地址值会留存但固件不执行 |
| 裸 IO 写被 GCU 覆盖导致无效 | 停服务+ACPI层写+高频重申(1s)，寄存器稳持 60 仍充到 90% |
| 需要 BatteryLimitation NVRAM 开关 | 寄存器层已彻底死心，NVRAM 开关即使存在也不会激活无实现的功能 |
| 内核隔离(HVCI/VBS)拦截写入 | 驱动正常加载、读写往返一致、三方对话(两进程两驱动读同值)证写入真实达 EC |
| 官方三档实际限充、仅 UI 显示 100% | 实测真实电流 10W 持续充电、真实容量上涨，无状态隐藏 |

### 当年 Linux「有效」的合理解释
当年 `charge_limit.sh` 的验证方式是「读回阈值寄存器一致」，未做真实电流/物理充电观察。
读回一致 ≠ 限充执行 —— 这正是本次踩的同一个坑。故当年「有效」属误判可能性极高。

## 二、EC 协议真相（权威，替换 v5.4 全域扫描记录）

### 充电相关寄存器（GCUService 反编译 + Linux 内核 uniwill-acpi.c 双重确认）
| 地址 | 语义 | 备注 |
|------|------|------|
| 0x7B9 | 充电上限 UP (=内核 EC_ADDR_CHARGE_CTRL) | GENMASK(6,0)=百分比, BIT(7)=REACHED标志 |
| 0x7D0 | 充电下限 DOWN (NEW, 内核未记录) | 本机与 0x7B9 一样不执行 |
| 0x7A8/0x7A9 | v5.4 误判地址 | 值会留存但无效果，**废弃** |

### 官方写通道（AcpiCtrl 反编译）
官方 GCUService 通过 `\\.\ACPIDriver`（UWACPIDriver.sys）的 DeviceIoControl 写 EC：
- `IOCTL_GPD_ACPI_ECREAD = 0x9C40A488`：输入 addr(u16 LE)，输出首字节=值
- `IOCTL_GPD_ACPI_ECWRITE = 0x9C40A48C`：输入 addr(u32 LE)+value(u32 LE) 共8字节，必须带输出缓冲

### 电池模式真相
官方三档 = 性能策略花名，非充电档：长效=HEALTHYMODE / 平衡=BALANCEDMODE / 工作站=PERFORMANCEDMODE。
切换只改 0x7A6(疑似实时功耗读数) 等性能侧寄存器，不碰充电寄存器。

## 三、SMU / CPU / GPU 调优结论（本机可行能力）

| 项 | 结论 | 通道 |
|----|------|------|
| CPU STAPM/PPT 功耗墙 | ✅ 可写，跟踪模式(office 35W/turbo 80W) | ryzenadj(需管理员+关火绒) |
| CPU tctl 温度墙 | ✅ 可写 | ryzenadj |
| CPU Curve Optimizer(CO) | ❌ ryzenadj --set-coall 崩溃(0xC0000005)，Rembrandt SMUv18 不兼容，且CO易失 | — |
| GPU 核心/显存时钟偏移 | ✅ NVAPI PerformanceStates20 用户态可写(每档 gpu_core/gpu_memory) | GHelper 内置 |
| GPU 功耗墙 | ❌ vBIOS 锁死 115W，nvidia-smi -pl 拒绝 | — |

### SMU 联动方案（已实现基础层）
- `smu_profile.json` 四档 office/gaming/turbo/custom 的 tctl/stapm/fast/slow
- `mr_daemon.py` 的 `_apply_smu()` 模式切换后调 ryzenadj 应用
- ⚠️ 已知缺口：ryzenadj 需管理员，daemon 免管理员运行时 SMU 层不生效；
  ryzenadj 位于临时目录 `C:\LHMtmp\ryzenadj`（整理时需迁移到项目内）

## 四、内核隔离(HVCI/VBS)影响结论

VBS 运行中 + 内存完整性(HVCI) Enabled。但对本项目**无影响**：
1. EC 是独立硬件(LPC/eSPI 总线 + ACPI 端口 0x62/0x66)，HVCI 只保护 CPU 内存代码执行，不拦外围 I/O
2. UWACPIDriver 是 OEM WHQL 签名驱动，HVCI 下正常加载(Status=OK)，读写往返一致
3. 真实拦截案例是火绒拦 ryzenadj 的 WinRing0(未签名老驱动)→驱动加载失败；与 HVCI 无关
